# BUG-122 — Brevo acepta el envío pero el error posterior no cambia el estado

- **Zona:** invitaciones/backend
- **Prioridad:** alta
- **Estado:** hecho
- **Asignado:** codex
- **Rama:** fix/BUG-122-brevo-error (frontend y backend)

## Descripción

BUG-120 funciona en producción: una invitación llegó a la bandeja de entrada con enlace/código correctos. En una prueba anterior, con remitente sin verificar, Brevo respondió 201 y messageId, por lo que la web mostró «¡Invitación enviada!». Después Brevo registró sent + error por remitente no válido. El webhook solo procesaba hard_bounce, invalid_email y blocked; la invitación permaneció como enviado aunque el correo no salió.

## Resultado esperado

- Procesar también el evento error de Brevo. Buscar por message-id y, sin coincidencia, por email y pendiente más reciente, con la lógica existente.
- Actualizar emailEstado a no_enviado, sin sobrescribir inexistente ni modificar invitaciones aceptadas (incluidas las que esperan reservas).
- No guardar ni registrar el reason completo, que puede contener PII.
- Mantener la etiqueta existente «El correo no se pudo enviar» en la lista de enviadas.
- Configurar el evento Error en el webhook transaccional de Brevo además de Hard bounce, Invalid email y Blocked.

## Archivos probables

Backend: mira-api/src/modules/invitations/service.js y routes.js, mira-api/test/invitacionesWebhook.test.js y docs/api.md. Frontend: test/invitacionEmailEstado.test.js; comprobar InvitePanel/InvitacionEmailEstado sin cambiar su comportamiento si ya sirve.

## Solución

- El webhook reconoce ahora `error` además de `hard_bounce`, `invalid_email` y `blocked`. Reutiliza la búsqueda por `messageId` (con/sin corchetes) y el fallback por email y pendiente más reciente.
- La transacción marca `emailEstado: "no_enviado"` cuando recibe error, preservando `inexistente`. Sigue sin modificar aceptadas ni las que esperan reservas, y no cae al fallback de otra pendiente si el message-id identifica una aceptada. Los eventos repetidos son seguros.
- El cuerpo validado descarta `reason`; no se guarda ni se registra completo. Se persiste únicamente `emailEvento`, uno de los cuatro códigos conocidos. Esto también impide que la respuesta 201 del envío sobrescriba un error que llegó mientras la petición a Brevo seguía pendiente.
- Frontend: comprobada la etiqueta existente de `no_enviado`, incluidas traducciones es/ca/en. No requiere cambios de UI. Añadido test de recuperación de la lista tras el error y render del aviso, conservando messageId y enlace. Como los eventos son asíncronos, el estado se ve al volver a cargar la lista.
- Tests backend: error → no_enviado; evento repetido; no sobrescribe inexistente; no cambia aceptadas/esperando reservas; fallback por email; token incorrecto 401; reason no persistido/logueado; error durante el envío seguido de 201/messageId conserva no_enviado.
- Validación: frontend `npm test` **195/195** y `npm run build` correcto. Backend `npm test` **287/287**, y `node --check` correcto en **80 archivos** de src. Se intentó `npm run build` del backend: no existe script build, ya que se ejecuta directamente con Node; no se añadió una fase de transpilación innecesaria.
- Worktrees propios desde main: `../codex-bug122` (frontend, base `69c4181`) y `../codex-bug122-backend` (backend, base `2f3515d`). Rama `fix/BUG-122-brevo-error` en ambos repos. Sin merge a main, sin envíos reales ni cambios de credenciales/configuración externa.

### Configuración del despliegue

1. Desplegar el backend de esta rama; las variables `BREVO_API_KEY`, `MAIL_FROM`, `BREVO_WEBHOOK_TOKEN` y `FRONTEND_URL` permanecen igual. No hay variables ni índices nuevos.
2. En Brevo → Email transaccional → Webhooks, editar el webhook existente y marcar **Error**, además de **Hard bounce**, **Invalid email** y **Blocked**. Mantener la URL protegida con el token actual (`/v1/invite/webhook/brevo?token=...`) y los eventos sin agrupar.
3. Probar el webhook Error y recargar la lista de invitaciones: debe mostrar «El correo no se pudo enviar. La invitación sigue creada.». Si ya estaba inexistente o aceptada, conservar su estado.
4. Mantener verificado el remitente/dominio en Brevo. Un 201/messageId acredita aceptación inicial del proveedor, no entrega final. El usuario ya confirmó una entrega real correcta de BUG-120; esta corrección cubre el rechazo posterior observado en la prueba anterior.

El motivo de Brevo no se guarda. Frontend 195/195 y build correcto; backend 287/287 (un fallo puntual en `SEC POST /v1/reviews sin token → 401`, ajeno a este cambio, no se repitió en dos pasadas más ni aislado).
