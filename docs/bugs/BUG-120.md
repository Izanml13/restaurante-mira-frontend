# BUG-120 — Invitar a un amigo: mensaje en el cuadro, lista que desaparece con F5 y el correo no llega

- **Zona:** invitaciones
- **Prioridad:** alta
- **Estado:** en revisión
- **Asignado:** codex

## Descripción
1) El resultado no se muestra dentro del cuadro. 2) La lista de invitaciones enviadas desaparece al recargar (F5). 3) El invitado no recibe ningún correo: el backend (modules/invitations) solo guarda el código en Firestore; no hay ningún proveedor de email configurado.

## Resultado esperado
1) Resultado dentro del cuadro: «¡Invitación enviada!» si Brevo acepta el correo; ante formato inválido, «No existe la dirección, compruebe antes de volver a enviar». 2) Lista persistida, cargada desde el backend al abrir Mi cuenta/Invitar y tras restaurar la sesión en F5. 3) Correo real con la API HTTPS de Brevo, `fetch` nativo, sin dependencias nuevas. Persistir `messageId` y `emailEstado` (`enviado`, `no_enviado`, `inexistente`). Sin clave, aviso y creación conservada. 4) Webhook Brevo protegido con token y comparación en tiempo constante: `hard_bounce`, `invalid_email` y `blocked` marcan inexistente únicamente las pendientes sin aceptación. Etiquetas traducidas es/ca/en en la lista.

## Decisión actual
Se sustituye Gmail SMTP/Nodemailer por Brevo HTTPS, porque Render Free bloquea los puertos SMTP 25, 465 y 587. El envío utiliza `POST https://api.brevo.com/v3/smtp/email`, `api-key`, `sender`, `to`, `subject`, `textContent` y `htmlContent`. Variables: `BREVO_API_KEY`, `MAIL_FROM`, `BREVO_WEBHOOK_TOKEN` y `FRONTEND_URL`. Se eliminan la dependencia Nodemailer y las variables SMTP anteriores.

## Archivos probables
Front: src/stores/useInviteStore.js, src/components/Cuenta.jsx, src/styles/cuenta.css. Back: mira-api/src/modules/invitations/, config/env.js, .env.example, docs/api.md, test/

## Solución

- Envío de texto y HTML con enlace/código usando `fetch` nativo y timeout de 15 segundos. `MAIL_FROM` admite email simple o `Nombre <email>`. Se escapan los datos del HTML. Sin clave/remitente o ante error de Brevo, se registra un aviso sin clave ni cuerpo de respuesta y la invitación sigue creada como `no_enviado`.
- Firestore guarda `messageId` y `emailEstado`. El estado `enviado` confirma aceptación por Brevo, no entrega al buzón. Un rebote recibido durante el envío no se sobrescribe al guardar el identificador. La lista y sus estados persisten tras F5; las creaciones nuevas normalizan el destinatario a minúsculas.
- `POST /v1/invite/webhook/brevo?token=...`: token obligatorio, comparación de hashes de longitud fija con `crypto.timingSafeEqual`, 401 si no coincide y límite de 120 peticiones/minuto por IP. Zod valida el cuerpo; eventos desconocidos reciben 200 sin consultar Firestore.
- `hard_bounce`, `invalid_email`, `blocked`: buscan por `messageId` (con/sin corchetes angulares) y, si no hay coincidencia, por email y pendiente más reciente. Una transacción marca `inexistente` solo si sigue pendiente y sin aceptación. No modifica aceptadas ni las que esperan reservas. El logger de peticiones elimina la query para no registrar el token.
- InvitePanel muestra la etiqueta de dirección inexistente o correo no enviado en cada invitación (es/ca/en). Si el envío inicial falla, lo indica también dentro del formulario. Los registros antiguos sin estado de entrega no reciben una etiqueta inventada.
- Tests de `fetch` simulado (URL, cabeceras, sender/to, enlace en texto y HTML, sin clave, errores, persistencia y rebote rápido), webhook (token, eventos, fallback, permisos de estado, rate limit y privacidad del log), y render real de la etiqueta con `react-dom/server` en tres idiomas. Sin claves ni envíos reales.
- Validación: frontend `npm test` **178/178**, `npm run build` correcto; backend `npm test` **280/280** y `node --check` en los **80 archivos** de src. El backend no define script `build`: `npm run build` devuelve Missing script; no necesita transpilación.

### Configurar en Render y Brevo

1. En Brevo, habilitar el correo transaccional si lo solicita la cuenta, añadir/verificar el remitente y generar una **clave API**, no SMTP. Si se usa dominio propio, autenticarlo con los registros indicados por Brevo.
2. En Render → mira-api → Environment: eliminar `SMTP_*`; añadir `BREVO_API_KEY`, `MAIL_FROM` (remitente verificado), `BREVO_WEBHOOK_TOKEN` (secreto aleatorio largo) y conservar `FRONTEND_URL` con la URL HTTPS pública del frontend. Credenciales solo en Render, nunca en Git ni frontend.
3. En Brevo → Email transaccional → Webhooks: crear un webhook **sin agrupar eventos**, URL `https://<backend-render>/v1/invite/webhook/brevo?token=<token_codificado_para_URL>`. Usar exactamente el secreto de `BREVO_WEBHOOK_TOKEN` y seleccionar Hard bounce, Invalid email y Blocked.
4. Redesplegar backend y frontend. La API usa HTTPS/443, compatible con Render Free. Backend: instalar dependencias y `npm start`; no hay fase de build.
5. Enviar una invitación de prueba, comprobar su `messageId`/estado y los logs de Brevo; probar el webhook y recargar la lista para ver la etiqueta. Consultar la cuota disponible de la cuenta Brevo.

Detalles: `mira-api/.env.example`, `mira-api/docs/api.md` §11. [API HTTPS de Brevo](https://developers.brevo.com/docs/send-a-transactional-email), [webhooks transaccionales](https://developers.brevo.com/docs/transactional-webhooks).
